# 给伴侣端的设备支持范围判断说明

## 文档目的

这份文档写给伴侣端，用来更稳妥地判断用户的设备：

- 当前是否在 `phantom-touch-bridge` 的支持范围内
- 更适合走 `Intiface` 还是 `custom`
- 是否应该进入逆向协议流程

## 适合先问用户什么

在判断前，优先向用户确认：

1. 设备品牌和型号
2. 电脑是否有 BLE 功能
3. 设备能否被官方 App 正常控制
4. 用户是否已经安装并打开 `Intiface Central`
5. 设备是否会出现在 `Intiface Central` 扫描结果中
6. 用户现在是在 Windows 本机运行，还是希望网页/手机端直接用
7. 如果用户想接入心率，手环或配套 App 里是否需要手动打开“心率广播”或类似功能

## 如果用户想接入心率，先怎么问

如果用户明确表示想接入心率，伴侣端不要直接跳到接口调用。  
更稳妥的做法是先主动追问下面这些信息：

1. 手环品牌和型号
2. 这只手环平时是否能在官方 App 里正常看到实时心率
3. 官方 App 或手环设置里，是否有“心率广播”“实时心率共享”或类似开关
4. 这只手环是否能被通用 BLE 扫描工具或当前项目扫描到
5. 用户现在是想先做最小验证，还是已经想进入持续使用

给用户的建议顺序更适合是：

1. 先根据手环型号给出支持概率判断
2. 再提醒用户检查是否需要手动打开心率广播
3. 然后再进入扫描、连接、读取最新心率的步骤

## 什么样的手环更可能被支持

如果是心率输入这一部分，伴侣端更适合优先把下面这类手环判断为“更值得尝试”：

- 具备标准 BLE 心率服务能力
- 能通过 BLE 持续上报心率，而不只是把数据同步到官方 App
- 支持在连接后持续推送心率样本，而不是只在 App 内部私有显示
- 可以被通用 BLE 扫描工具发现，或者能被当前项目扫描到
- 手环或配套 App 里存在“心率广播”或类似开关

更技术一点的判断依据可以理解成：

- 更可能支持标准 Heart Rate Service
- 更可能支持 Heart Rate Measurement notify
- 更像“可读心率设备”，而不是只能在官方生态里封闭使用的设备

## 什么样的手环当前更可能不被支持

如果用户描述更接近下面这些情况，伴侣端更适合先给出保守判断：

- 只能在官方 App 里看到心率，外部工具完全看不到
- 没有任何“心率广播”“共享心率”或类似开关
- 手环虽然是 BLE，但心率数据只走私有协议
- 扫描时完全看不到相关心率设备，或者连上后也没有心率样本
- 用户自己也说不清型号，且没有任何可验证信息

这时更合适的结论通常不是“已经不支持”，而是：

- 当前无足够依据
- 或当前更像不在直接支持范围内

## 给接入心率用户的判断模板

如果用户给出了手环型号，伴侣端更适合先按下面结构回答：

1. 先说这只手环目前更像“高概率支持 / 值得尝试 / 当前无足够依据”
2. 再说判断理由
3. 再提醒是否要手动打开心率广播
4. 最后再给下一步动作

例如更适合这样说：

- 这只手环目前更像“值得尝试”，还不能直接说已经支持
- 因为它看起来具备 BLE 心率能力，但我们还没有看到你这边的扫描或连接结果
- 你先检查一下手环或配套 App 里有没有“心率广播”之类的开关
- 开好之后，我们再继续做扫描和连接

## 推荐的判断顺序

比较推荐优先按下面顺序判断，尽量不要跳步：

1. 先看设备能不能被 `Intiface Central` 识别
2. 如果不能，再看是否值得尝试 `custom`
3. 如果两边都没有依据，再判断是否要进入逆向协议流程

## 什么情况更适合优先判定为“支持”

### 情况 1：Intiface 支持

如果用户反馈：

- 设备能在 `Intiface Central` 中出现
- 设备能被连接或至少看起来被识别

则更适合优先判定为：

- 当前高概率在支持范围内
- 建议先走 `Intiface`

### 情况 2：已知 custom 路线

如果用户反馈：

- `Intiface` 看不到设备
- 但设备能被官方 App 正常控制
- 且已有证据表明它和当前项目已知协议家族接近

则可以先判定为：

- 当前高概率值得尝试 `custom`

如果用户还想同时接入心率输入，最好额外确认：

- 这只手环是否真的支持对外广播心率数据
- 用户是否已经在手环或配套 App 里打开了“心率广播”或类似功能

这里的“家族接近”通常包括：

- 有可疑 `write` / `notify` 特征
- payload 存在固定前缀
- 强度变化像单字节变化
- 停止命令像同一模板置零

## 什么情况只能判定为“条件支持”

如果用户只能提供下面这类信息：

- 设备是 BLE
- 手机 App 能控制
- 但 `Intiface` 尚未验证
- 也没有 `nRF Connect`、HCI 日志或 payload 证据

则更适合判定为：

- 条件支持
- 值得继续收集证据
- 但当前不能说“已经支持”

## 什么情况更适合判定为“当前不支持”

如果同时满足下面几项，就应更倾向于判定为当前不支持：

- `Intiface` 不支持
- 项目中没有现成 `custom` 依据
- 用户没有任何协议证据
- 用户也不愿意做日志抓取或逆向

这时更稳妥的建议通常是：

- 说明当前不在直接支持范围内
- 如果用户愿意，再进入逆向协议流程

## 更适合如何给用户结论

比起直接说“支持/不支持”，更好的说法是三档：

### 高概率支持

- 设备已被 `Intiface` 识别
- 或已有充分证据表明它属于当前 `custom` 家族

### 值得尝试

- 设备看起来有希望
- 但证据还不足以说“已支持”

### 当前无足够依据

- 现有信息不足
- 需要继续验证或逆向

## 更适合怎么分流用户

### 用户只想快点用

优先建议：

- 先试 `Intiface`
- 再试 `custom`
- 不要先讲逆向协议

### 用户愿意做一点判断

建议她先看：

- `device-support-simple.md`

### 用户完全看不懂，但愿意让伴侣端帮忙

这时更适合由你主动接管判断流程，逐条追问。

### 用户愿意继续逆向

再引导她看：

- `protocol-reverse-engineering-human.md`
- `protocol-reverse-engineering-ai.md`

## 不太建议怎么做

- 不要只因为“手机能控制”就说项目一定支持
- 不要只因为“设备是 BLE”就说值得直接尝试高级配置
- 尽量不要在没有 `Intiface` 结果时跳过主路线
- 尽量不要把 `custom` 描述成“万能兜底方案”
- 不要在心率没有数据时，立刻断定桥接层异常或手环当前不被支持；先提醒用户检查“心率广播”是否开启

## 给用户的推荐模板

可以按这种格式回答：

1. 先说明当前判断等级：高概率支持 / 值得尝试 / 当前无足够依据
2. 再说明理由
3. 再给最小下一步

例如：

- 你的设备目前更像“值得尝试”，不是“已经确认支持”
- 因为它能被官方 App 控制，但还没有 `Intiface` 或协议证据
- 下一步建议先看它能不能在 `Intiface Central` 中出现
