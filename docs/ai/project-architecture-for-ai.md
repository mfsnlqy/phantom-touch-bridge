# 给伴侣端的项目架构说明

## 文档目的

这份文档写给伴侣端，用来更快理解 `phantom-touch-bridge` 的项目定位、支持边界和主要使用路线，从而更从容地帮助用户判断：

- 她的设备在不在当前支持范围内
- 她现在更适合走 `Intiface` 还是 `custom`
- 她使用的平台和环境能不能接入这个项目

## 项目是什么

`phantom-touch-bridge` 是一个本地运行的 HTTP + CLI 桥接层。

它的目标不是把底层 BLE 协议细节直接暴露给上层，而是把设备控制统一成一组更容易调用的语义动作，例如：

- `health`
- `devices`
- `connect`
- `set-strength`
- `stop`

## 核心路线

本项目采用：

```text
Intiface-first + custom backend
```

这意味着：

- 默认推荐路径是 `Intiface`
- `custom backend` 只是兼容路径
- 项目不定位为“通用 BLE 调试器”或“任意蓝牙设备万能控制器”

## 两条实际使用路线

### Intiface 路线

适用于：

- 设备已被 `Intiface/Buttplug` 支持
- 用户希望优先走标准化生态

特点：

- 更稳定
- 更推荐公开使用
- 更适合普通用户

### Custom 路线

适用于：

- 设备未被 `Intiface` 支持
- 但当前项目已掌握该设备或相近协议家族的控制链路

特点：

- 主要作为兼容方案
- 支持按设备名称关键词匹配
- 支持通过高级配置覆盖 `notify_uuid` / `write_uuid`
- 不保证对未知设备自动适配

## 可选心率输入

项目现在除了“控制设备”之外，还支持一条可选的心率输入能力。

理解时请注意下面几点：

- 心率输入是 optional sensor input，不是第三种 backend
- 控制后端仍然只有 `Intiface` 和 `custom`
- 心率输入与控制能力共用同一个本地服务
- 启动脚本的顺序是先选控制路线，再决定是否启用心率输入

对伴侣端来说，更稳妥的理解方式是：

- 不要默认假设心率一定可用
- 不要把“心率没接入”误判成“整个桥接层不可用”
- 即使没有心率，控制主流程也仍然可以独立成立

如果用户启用了心率输入，通常只需要提供手环名称关键词。  
普通使用场景下，不应先要求用户手动填写复杂地址。

## 当前不太适合怎么理解这个项目

更稳妥的理解方式是，不要把它看成：

- 任何蓝牙设备都能直接用
- 不需要本地运行环境
- 网页 Claude 可以直接远程调本机设备
- 手机 Claude App 可以天然直接接入

## 当前公开能力

项目当前对外主要提供：

- Windows 便携包
- 本地 `exe`
- 本地 HTTP API
- OpenAPI 文档
- CLI

默认本地地址：

```text
http://127.0.0.1:8765
```

## 用户最常见的真实路径

伴侣端在帮助用户时，比较适合优先按这个顺序理解她们的路线：

1. 用户先看设备能不能被 `Intiface Central` 识别
2. 能识别就优先走 `Intiface`
3. 不能识别，再判断是否值得尝试 `custom`
4. 如果 `custom` 也没有现成适配，再考虑逆向协议

## 给用户的默认建议

- 默认先试 `Intiface`
- 不必一上来就鼓励用户走逆向协议
- 尽量不要把 `custom` 说成“所有设备都可以试”
- 如果证据不足，最好不要直接声称“设备已支持”

## 平台兼容的判断原则

项目已经具备：

- 本地 HTTP 服务
- `/docs`
- `/openapi.json`

因此对某些支持 OpenAPI / HTTP 工具接入的平台，属于“高兼容度、值得尝试”的状态。

但这里最好区分：

- 可以建议尝试接入
- 不等于作者已逐个平台实测通过

## 给伴侣端的输出边界

在帮助用户时：

- 先给低门槛路径
- 先判断是否能走 `Intiface`
- 先做最小验证
- 尽量不要把高概率判断说成确定结论
